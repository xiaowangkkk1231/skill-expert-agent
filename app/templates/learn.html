第一章

为什么 description 要写两件事

SKILL.md 不是被整个读进去的。它在三个时机被分段加载，每一段只读一部分。 明白这个顺序，就明白那些写法要求不是谁定的规矩，是被加载方式逼出来的。

01

开机就扫：只读 name 和 description

所有 skill 的头部信息在会话开始时就全部铺进系统提示，正文一个字都不读。

→ 所以 description 得同时说清"干什么"和"什么时候用"。只写一半，它就永远匹配不上，后面写得再好也没机会被读到。

02

匹配上了，才读正文

头部命中之后，Markdown 正文才被装进当前上下文。这时候才轮到细节规则生效。

→ 所以正文要控制在 500 行内。塞太满，挤掉的是本该留给任务本身的上下文。

03

执行时，按需取附件

同目录下的 scripts / docs 只在真正被调用时读取，平时完全不占位置。

→ 长文档和可执行脚本放这里，正文只留"什么时候去取"。

第二章

四类要求，四个格子

人对着 AI 说的话，去掉闲聊和任务，剩下的期待只分四种。 而这四种刚好能落进正文的四段——所以"归类"和"落格"本来就是同一步。

你嘴上说的

偏好
语气、长短、正式与否。决定"像不像你"。
约束
禁止或必须，是否决性的。决定"能不能用"。
工作流
先后顺序、必须经过的步骤。决定"按不按流程"。
示例
好坏两版对照。决定"拿不准时听谁的"。

文件里落的

→
## 必须避免　收约束
→
## 风格要求　收偏好
→
## 工作流　收工作流
→
## 示例对照　收示例

一句话同时像两类时，只留在更硬的那类：能写成"不要 X"的算约束， 说清先后顺序的算工作流，只有举了具体例子的才算示例。

第三章

五步，每一步都能看见

每一步只做一件事，都有自己的界面和输出。你能看着它从第 1 步走到第 5 步，而不是等一个转圈。

01

圈句

按句切开人类发言，剔掉寒暄、"帮我写一段"这类任务请求，剩下的按四类打标，每条留住原话。

02

归档

同一件事的多种说法合成一条，重复的去掉。这一步是代码算的，不是模型拍的，跑十次结果一样。

03

落格

四堆各进各的段落，条数决定篇幅——内容多长，不由模型即兴发挥。

04

成稿

name → description → 正文，一个字段一个字段往外吐，前面的字段先落地。

05

体检

格式、焦点、体量、原话溯源、规则互斥，全过一遍才允许导出。

第四章

出门前的 14 项体检

前 12 项查格式，和 SKILL.md 的字段约定一一对应；后 2 项查语义，专门盯模型最容易犯的两种错。

字段检查项级别判定
namename-requirederror必填
namename-too-longerror超过 64 字符
namename-formaterror仅允许小写字母 / 数字 / 连字符
namename-reservederror用了 anthropic / claude / openai / skill / agent 这类保留词
namename-too-shortwarn少于 4 字符，不利于被检索到
descriptiondesc-requirederror必填
descriptiondesc-too-longerror超过 1024 字符
descriptiondesc-missing-whenwarn没写"什么时候用"，缺少适用于 / when / 用于 这类词
descriptiondesc-multilinewarn折行了，部分 YAML 解析器会读坏
bodybody-requirederror必填
bodybody-too-longwarn超过 500 行，该拆成子 skill
bodybody-no-h1warn缺一级标题
原话signal-unverifiedwarn这条要求在对话里找不到出处，可能是模型自己总结的
原话rule-conflictwarn两条约束互斥，比如"必须用 X"和"禁止 X"同时存在

真正拉开差距的是 signal-unverified：它把"听起来像你的要求"和"你确实说过"分开。 没有这一步的提炼，只是让模型写了一篇关于你的作文——写得像，但不一定发生过。
